## Context

See `proposal.md` for motivation. `@et/core` exports `WeekPlan`, `validateWeekPlan`, `RunState`, `advanceSeason`, `SeasonAdvanceResult`, `startSeason`, `createRng`, `generatePerformer`, `quoteWeeklyRate`, `createIncidentState` and `collectiveMorale` from its package root. `advanceSeason` calls `advance` with the season calendar, returns `advance.weeks`, `advance.reasons`, `advance.stoppedAt`, `runState` (whose `week` is already the NEXT week) and a tagged active/completed `season`. The week loop accepts only blocks of 4–6 entries even if the remaining season has fewer weeks, and refuses to advance pending incidents or uncovered engagements. A marked week ahead is a stop on the preceding week, not permission to invent a contest.

The active #45 `season-contest` change declares `week.ts`, `season.ts`, `index.ts`, core tests, `docs/INDEX.md` and the `season-contest`/`season-calendar` live specs. `week-shell` declares none of those paths or requirements. Its implementation may consume the eventual public API after #45 archives, but must not change the core API to serve UI. The current shipped `standard` template has two unsupported `series` weeks. This shell will expose a blocked boundary rather than claim to deliver a complete playable season before a series-format capability exists.

## Goals / Non-Goals

**Goals:**

- A browser screen that plans and advances a real seeded run and renders its returned values, week results and all stop reasons.
- A shell-owned command/state boundary reusable by future #50 contest and #51 incident surfaces without moving their behavior into #38.
- A comparable two-layout visual probe and a reproducible physical-device measurement procedure before final art (#37).

**Non-Goals:**

- Core refactors, mechanic changes, final art/grid/camera, a contest screen, an incident-choice modal, a general engagement-management screen, Capacitor packaging, local saves, a second language, or the implementation of localization in #38.
- Fabricated settlement, incident choice, contract renewal, series outcome or season restart to make Continue appear to work.

## Decisions

### Spec boundary and paths

Use a new live capability `game-shell`. It describes the presentation and input boundary, not the week equations. Infrastructure-only `skip_specs: true` would omit observable interaction guarantees; modifying `week-loop` would make a domain-neutral rule depend on browser UI. `packages/shell` is a pnpm workspace member already matched by `packages/*`. Its `package.json` exports no core API; it depends on `@et/core` through the package root only, `pixi.js` 8 and Vite. Browser entry is `packages/shell/index.html` → `src/main.ts`; `vite.config.ts` sets the package root and build output. Root `pnpm dev` invokes the shell's dev command; root `pnpm verify` runs the shell production build and shell typecheck in addition to the existing checks. Keep the root Node-only `tsconfig.json` free of DOM globals by limiting its package include to `packages/core/**/*.ts`; add `packages/shell/tsconfig.json` for DOM and Vite browser types, and typecheck both projects explicitly. Add eslint import restrictions for shell internals and preserve the present core I/O/rendering bans. `pnpm-lock.yaml` records the dependencies. No `pnpm-workspace.yaml` or `docs/INDEX.md` edit.

Shell source responsibilities: `src/content.ts` loads JSON from the existing `content/` tree through Vite's eager glob (activities, regions, name pools, traits, disciplines and `seasons/standard.json`), checks required shapes/references with the existing content JSON schemas via Ajv, and supplies typed values to `src/run.ts`. The repository validator is the canonical whole-tree referential gate and runs before both dev and production build; a browser load failure also yields a visible diagnostic, not a silent `undefined`. Never bundle a Node `fs` reader or import `tools/sim-harness` into the client. `src/run.ts` creates a deterministic first run from one declared seed, the validated origin, discipline, template and rates: `createRng(seed)` for performer generation followed by its `state()` in `RunState`, the named `season-calendar` stream for `startSeason`, `createIncidentState(seed)`, and `quoteWeeklyRate` for initial engagements. A fixed development seed (`week-shell-38`) and an optional explicit `?seed=` value make reload reproducible; reload starts a fresh run and says so, because persistence is #20/#53. No system random seed, no clock-derived seed, no second RNG in Pixi. Default act-one roster comes from the shipped discipline's declared participant count; the performance fixture adds visual figures but never overwrites career state.

`src/session.ts` owns the committed `{runState, season}`, the current `WeekPlan` draft with an absolute `startWeek`, last `AdvanceResult`, and the screen mode. `src/week-panel.ts` renders DOM from session snapshots and sends user intents to the session; `src/scene.ts` receives read-only snapshots for geometry only; `src/layout.ts` holds the two view transforms. `src/main.ts` wires boot, error surface and disposal. A future contest/incident view can replace the panel via a shell view slot, while the same session remains the only run owner; there is no general router in #38. Forbidden: imports from shell into core, imports of `@et/core/src/*` into shell, `tools/**` into browser, and any direct core transition call from Pixi or DOM components. The session is the sole caller of `advanceSeason`; no UI-local implementation of slot, morale, money, threshold, recovery or stop formulas.

### State machine and commands

Modes are `loading`, `editing`, `advancing`, `stopped`, `blocked`, `error` (tagged union, with mode-specific data). `loading` owns no usable run. `editing` has a committed run and draft; `advancing` retains that snapshot but freezes controls and holds an invocation token; `stopped` carries a committed `SeasonAdvanceResult`, a reason list and an editable future draft; `blocked` carries the committed result/state and a specific unresolved core boundary; `error` carries a diagnostic and last committed snapshot if one exists (boot failure has none). `stopped → editing` is an explicit Edit/Continue intent; `blocked → editing` is allowed only after a future resolution operation actually commits new core state. A rejected plan returns to `editing` with a message, never as a successful stop. Unknown season/stop tags surface as `error`, fail closed, and do not route to a generic Continue.

The sheet's `collapsed | expanded` presentation is orthogonal to these core-command modes, not a seventh simulation state. Successful boot starts collapsed with a compact current-state summary; an explicit DOM toggle expands the draft without resetting it. A successful advancement commits first, then collapses the sheet so the scene, committed values and all returned reasons are visible; reopening shows only unexecuted assignments. A rejected plan keeps the sheet expanded for correction, and a blocked result keeps its reason and disabled Continue visible in either position. Toggling only changes presentation; it consumes no RNG, never dispatches to core and does not bypass the revision/single-flight guard.

Start a draft of four weeks at `runState.week`, with no assignments; allow selecting 4, 5 or 6 weeks. Each row holds ordered activity IDs and (for single-member targets) member IDs, looked up against validated catalog/roster when materializing the core `WeekPlan`; never store a duplicate activity definition in mutable draft state. The panel permits additions, removals and reordering only for absolute weeks >= `runState.week`. Before invoking core, check current mode, a monotonically increasing render/session revision and whether a command is already in flight; synchronously set `advancing` and disable dispatch before calling `advanceSeason(runState, season, plan, {})`. No optional sensitivity mask or fabricated incident input in #38: omitted `incidentInput` disables incident selection by the existing core contract until #51; if a pending incident enters via a future view, honor the blocker. Avoid asynchronous UI-derived optimistic patches. The core call is synchronous today; keep the guard so a click and keyboard activation on the same render or a queued old handler cannot execute twice. On success commit `result.runState` and `result.season` atomically, verify the returned weeks are contiguous from the submitted start and end at `runState.week - 1`, record `result.advance.reasons` and `stoppedAt` verbatim, and discard the executed draft prefix of exactly `result.advance.weeks.length`. Do not call core again while rendering. A malformed result is an error, not a fallback.

If the remaining draft has fewer than four entries, append empty future rows up to four, retaining existing future assignments and identities; the new plan starts at the committed `runState.week`, not the old block start. Empty rows beyond the materialized season calendar are disabled in the editor and exist only to satisfy the core's block-length contract: the season boundary stops execution before them. Past rows are read-only from returned `WeekResult` evidence, not reinserted into a plan. `block-ran-out` opens a fresh four-week draft. `season-ended` shows the completed state; no automatic `startNextSeason`. For `contest-ahead`, pending incidents, expired engagements, completed-season or unsupported series boundaries, show a distinct blocked message and disable Continue. A future #50 adapter can settle the marked entry using its own public core operation before returning control; #51 can commit a real `resolveIncident` result. Neither is pre-implemented or emulated here. The default shipped season can advance through genuine ordinary weeks until these blockers and cannot claim to complete the whole season.

### Pixi/DOM, responsive layout and probes

PixiJS 8 owns the room backdrop and labeled geometric figures, at most ambient deterministic visual movement independent of the simulation RNG. It has no click targets or authoritative text. A draft assignment may highlight its named figure as a clearly non-authoritative plan preview, without projecting spent energy, morale or money. Only after `advanceSeason` returns may a figure react to committed state or returned `WeekResult` evidence; geometry is a temporary expressiveness probe, not a claim that every pose or animation is implemented. The DOM owns a compact current-state/reason summary, an expandable semantic week-plan sheet, activity and participant selectors, returned results, slots, per-member energy/morale, `collectiveMorale` from core, balance and accessible status announcements. One shared Continue action stays outside the scrolling area in both sheet positions; do not mount competing buttons or duplicate dispatch handlers. Every game state shown in the scene also has a DOM numeric/text duplicate. The canvas sits behind the sheet with `pointer-events: none` and `aria-hidden`; the DOM alone handles pointer/keyboard input. Catch renderer initialization/ticker failures; retain working DOM and show a visible scene error, without forging run state.

Use a 390×844 CSS-pixel portrait **reference viewport for layout inspection**, not a claim about any target phone. Set the viewport meta for device width and `viewport-fit=cover`, respect `env(safe-area-inset-*)`, and give controls at least 44×44 CSS-pixel active targets. On a narrow portrait screen, the collapsed sheet holds the state summary and toggle below a visibly larger scene; expanding it overlays the lower scene but leaves a meaningful preview visible at the top. The expanded sheet scrolls its plan independently, with a labelled expand/collapse control and one persistent bottom Continue bar above the safe-area inset; neither the action nor the final plan row may sit under the bar. The current stop reason stays in the persistent summary instead of vanishing below the fold. At wider widths, the same sheet may sit alongside the scene with a capped readable line width; opening it never changes run state. Landscape remains a scrollable fallback with reachable controls. `ResizeObserver` and orientation changes recompute the visible scene rectangle before whole-number scaling; the probe-only logical scene is 320×180, scaled by `max(1, floor(min(availableWidth / 320, availableHeight / 180)))`. On a smaller viewport, clip/scroll the decorative scene rather than fractionally scaling it, but keep the DOM summary readable and record which figures disappear. This is not a final art pixel grid.

Support `?layout=front` and `?layout=isometric` in the probe; front is the default first-screen arrangement in line with `design/ui.md`'s first-version no-isometry constraint, not a final art verdict. Both use the same figures (15 for the act-three profile), labels, DOM sheet, seed, viewport and input sequence. Compare **both** collapsed observation and expanded editing: visible scene rectangle, recognizable people and planned/committed cues, occluded figures/labels, time and mis-taps when editing a future activity, visibility of the returned consequence, and matched frame-time distributions. Give #37 paired screenshots of both sheet positions with measured scene/exclusion zones and legibility notes. The front/isometric probe does not select a camera, sprite silhouette, animation budget or tile grid; the sheet arrangement likewise does not require tapping small figures to play.

### Localization decision

Compare (a) **i18next**: framework-independent TypeScript/Vite/Capacitor-compatible runtime, JSON resources, interpolation/fallback, modest runtime dependency; (b) **Lingui**: extract/compile catalogs, useful tooling but extra compile setup for a frameworkless first screen; (c) **FormatJS `intl-messageformat`**: excellent ICU formatting, but would require us to build locale/catalog loading and fallback around its formatter. Select i18next for a later localization change, with `en` as fallback language, `en.json`/`<locale>.json` resources under `packages/shell/src/i18n/`, stable semantic keys such as `week.continue`, `week.plan.activity`, `week.reason.contestAhead`, `week.error.content`, and complete phrases with named interpolation rather than concatenated fragments. In #38 do **not** install or implement i18next or write a homegrown translation helper. English UI copy lives at its rendering sites in `src/week-panel.ts`/`src/main.ts`, content labels remain in `content/`; stable keys are reserved in this design for migration. The first actual locale extension moves that English copy to `en.json` and installs i18next without changing simulation. Player-facing copy follows `design/tone.md` (plain, lively English, precise numeric consequences).

### Performance protocol and checks

The **layout reference** is 390×844 CSS px. A physical device run uses its real measured CSS viewport (record width, height, DPR, safe-area insets and orientation); never impersonate 390×844 with desktop emulation or claim physical equivalence if it differs. For each named physical iOS and Android model, record OS build, Safari/WebView or Chrome version, browser engine, device power/thermal state, screen refresh rate and measurement tool/version. Run the production Vite build locally via HTTPS-accessible test host on the actual device, fresh-load the same explicit seed and `?layout=` variant with 15 geometric figures and the same real DOM sheet. Warm for 20 seconds, sample 60 seconds, repeat three times per layout with full reload. Identical script per run: observe collapsed scene 0–10 s; expand sheet and scroll the plan down/up 10–20 s; assign one valid future activity at 25 s and close the sheet at 30 s; press Continue once at 40 s; observe the returned scene and reason until 60 s. Capture `requestAnimationFrame` frame intervals (median, p95/p99, dropped frames and FPS = frames/elapsed seconds) and profiler frame timings; collect the maximum available process or JS heap footprint, specify which kind, sampler and time window, and label unavailable GPU/process-memory metrics `unavailable` rather than replacing them. Record screenshots and raw samples in #38 PR-2 review notes for #37; no invented target FPS threshold or measured device results in PR-1. Specific physical model names/OS/browser builds remain an **external execution prerequisite** supplied by the owner of the iOS and Android devices, not an unresolved architecture choice. The #38 acceptance of an on-device profile cannot be claimed until both device runs have been observed.

Unit tests focus on session transitions, revision guards, immutable executed weeks and blocked boundaries; integration tests use the real core and shipped validated content to prove one activation produces exactly one transition, continuation starts at the returned `runState.week`, and displayed values equal it. Browser smoke opens `pnpm dev` on a phone-sized viewport, expands the sheet, edits a block, collapses it without losing draft/core values, advances once, observes the collapsed scene plus all returned reasons, reopens for future edits and tries a stale second activation; repeat at narrow and wide viewport and capture both layout probes in both sheet positions. On a real phone, check character/activity cues are legible when observing, the expanded sheet leaves a useful preview and future-week editing is usable by touch; a green FPS profile does not substitute for this inspection. Separate manual physical touch/device profile evidence from viewport emulation. A source-boundary check/lint restriction forbids shell simulation formulas and direct core internals; test observable outcomes rather than copying fields through mocks. The existing `pnpm verify` plus a production shell build are required before PR-2.

## Risks / Trade-offs

- The real shipped season can stop at an encounter or unsupported series and stay blocked until #50/series work; this is a visible dependency, not a fake completion path. Incident selection is disabled explicitly until #51; a future pending incident still displays a blocker.
- UI-only draft and seed reset on reload until #20/#53; an explicit fresh-run notice prevents accidental claims of persistence.
- Runtime JSON validation in a browser and the build-time canonical validator share schemas but not an I/O implementation; do not duplicate balance or simulation rules while adapting content.
- A bottom sheet can hide the very character cue that made the scene worth drawing, while a larger scene can squeeze the plan on short phones. Keep one visible preview and the persistent reason/action in both positions, then compare legibility and touch-editing on actual devices; a 15-figure FPS number alone cannot decide the composition.
- Two geometry probes add temporary rendering code but no lasting art authority. Physical FPS/memory results depend on access to real named devices and profiler APIs; unavailable counters remain gaps, not fabricated measurements.
- `season-contest` may archive after this proposal's base: PR-2 must rebase and adapt shell-only callers to public exports, without touching any #45 path.
